# Requirements Document — Video Control and Preview

## Introduction

This spec extends Invisible A/V Booth with real-time video preview and camera control capabilities. It introduces two major features: (1) a live OBS stream preview widget that allows volunteers to see exactly what is being broadcast, and (2) an NDI/VISCA camera control system with live preview, PTZ controls, AI tracking toggles, and preset management.

This spec depends on the foundational platform delivered by the `livestream-control-system` spec (authentication, dashboard, widget grid, event bus, notification system) and the `multi-platform-streaming` spec (RTMP relay, OBS streaming state, `ConnectionStatus` model). It adds two new widgets to the dashboard grid and introduces a new Camera Hardware Abstraction Layer (HAL) on the backend.

Video preview streams are delivered via dedicated WebSocket connections (separate from the command/event Socket.io connection) using fragmented MP4 (fMP4) with MediaSource Extensions (MSE) in the browser. This achieves sub-500ms latency on a LAN, which is critical for camera PTZ control where delays cause operator overshoot. The server uses FFmpeg for transcoding/remuxing; hardware-accelerated encoding (VA-API, QSV, NVENC) is auto-detected at startup and used when available. Preview resolution defaults to 720p (configurable via code constant) since dashboard widgets render at far smaller dimensions — sending 1080p would waste bandwidth and CPU for no visual benefit.

No FFmpeg transcoding process is spawned unless at least one client is subscribed to that stream. Processes are torn down after the last subscriber disconnects (with a short grace period to avoid thrashing on page refresh).

## Glossary

- **fMP4 (Fragmented MP4)**: A variant of the MP4 container format that splits the media into small independently-decodable fragments, enabling low-latency streaming via progressive download or WebSocket delivery.
- **MSE (MediaSource Extensions)**: A browser API that allows JavaScript to feed media segments to a `<video>` element for playback, enabling custom streaming protocols without browser plugin support.
- **Preview Stream**: A real-time video (and optionally audio) feed delivered from the backend to the dashboard for monitoring purposes. Not the same as the broadcast stream sent to platforms.
- **NDI (Network Device Interface)**: A royalty-free IP video protocol by Vizrt for high-quality, low-latency video transport over LAN. Used for both receiving camera video feeds and sending PTZ control commands.
- **VISCA (Video System Control Architecture)**: A serial/IP camera control protocol originally by Sony, now an industry standard for PTZ camera control. Supports absolute/relative positioning, speed control, preset store/recall, and position inquiry.
- **PTZ (Pan/Tilt/Zoom)**: The three mechanical axes of camera movement. Pan is horizontal rotation, tilt is vertical rotation, zoom is optical magnification.
- **Camera HAL (Hardware Abstraction Layer)**: The backend service that normalizes NDI and VISCA protocol differences behind a common interface, so widgets and presets operate protocol-agnostically.
- **Dead-Man's Switch**: A safety mechanism where continuous PTZ movement requires periodic keepalive signals from the client. If keepalives stop (e.g., network drop), the backend automatically issues a stop command to prevent runaway camera movement. The timeout is tuned for WiFi tablet use (not wired assumptions).
- **Virtual Joystick**: A circular touch zone for pan/tilt control where distance from center determines speed and angle determines direction. More natural for touch interfaces than discrete D-pad buttons, supports diagonal movement inherently, and provides proportional speed control.
- **Adaptive Speed**: PTZ movement speed that automatically scales inversely with zoom level — slower when zoomed in (fine control), faster when zoomed out (coarse re-framing).
- **Preview WebSocket**: A dedicated WebSocket endpoint (separate from the Socket.io command connection) used exclusively for binary video stream delivery. One endpoint per source (OBS, each camera). Authenticated via the same HttpOnly JWT cookie used by all other connections.
- **Fan-Out**: The server pattern of running a single FFmpeg transcode per source and distributing the output to all subscribed WebSocket clients, avoiding redundant transcoding.
- **Hardware Encoder Probe**: A one-time startup check that queries FFmpeg for available hardware-accelerated encoders (VA-API, QSV, NVENC) and caches the result for the lifetime of the process.

## Requirements

### Requirement 1: Video Preview Infrastructure

**User Story:** As a system architect, I want a shared infrastructure for delivering real-time video previews to dashboard widgets, so that both OBS and camera previews use the same efficient delivery mechanism without duplicating transcoding logic.

#### Acceptance Criteria

1. THE Backend SHALL expose dedicated WebSocket endpoints for video preview streams, separate from the Socket.io command connection. Each video source (OBS relay, each camera) SHALL have its own WebSocket endpoint path (e.g., `/preview/obs`, `/preview/camera/{cameraId}`).
2. THE Backend SHALL transcode/remux source video into fragmented MP4 format using FFmpeg, with flags `-movflags frag_keyframe+empty_moov+default_base_moof` to enable immediate playback without requiring the full file header.
3. THE Backend SHALL define a code constant `PREVIEW_RESOLUTION` defaulting to `{ width: 1280, height: 720 }`. FFmpeg SHALL scale the source to this resolution for all preview streams. This is configurable by changing the constant — no runtime UI is provided.
4. THE Backend SHALL probe FFmpeg's available encoders at startup (once, cached for process lifetime) by executing `ffmpeg -encoders`. IF a hardware encoder is detected (in priority order: `h264_vaapi`, `h264_qsv`, `h264_nvenc`), THE Backend SHALL use it for all preview transcoding. IF no hardware encoder is available, THE Backend SHALL fall back to `libx264` with `-preset ultrafast`.
5. THE Backend SHALL log at INFO level which encoder was selected at startup (e.g., "Video preview using hardware encoder: h264_vaapi" or "Video preview using software encoder: libx264 ultrafast").
6. THE Backend SHALL NOT spawn an FFmpeg process for a preview source until at least one WebSocket client connects to that source's endpoint. WHEN the last WebSocket client disconnects, THE Backend SHALL wait a grace period of 3 seconds before terminating the FFmpeg process. IF a new client connects within the grace period, the existing process continues without interruption.
7. THE Backend SHALL fan out the FFmpeg output to all connected WebSocket clients for that source. A single FFmpeg process per source serves all subscribers — multiple clients watching the same preview do NOT spawn multiple transcoding processes.
8. THE Frontend SHALL use the `MediaSource` API (MSE) to receive fMP4 chunks over WebSocket and feed them to a `<video>` element for playback. THE Frontend SHALL handle `MediaSource` buffer management: segments older than 2 seconds SHALL be removed from the SourceBuffer to prevent memory growth and keep preview latency under 500ms. If the buffer grows beyond 3 seconds (e.g., due to a processing stall), THE Frontend SHALL seek the video element to the live edge to prevent stale frames from accumulating. This is critical for tap-to-center accuracy — the volunteer must see the camera's current position, not where it was seconds ago.
9. WHEN an FFmpeg preview process exits unexpectedly, THE Backend SHALL attempt to restart it after a 2-second delay if subscribers are still connected. IF the process fails to start 3 consecutive times, THE Backend SHALL close all subscriber WebSocket connections with a descriptive close reason and stop retrying until a new client connects.
10. THE Backend SHALL verify FFmpeg is available on the system PATH at startup (shared check with the multi-platform-streaming spec's relay requirement). IF FFmpeg is not found, preview functionality SHALL be unavailable and widgets SHALL display an appropriate error state.
11. WHEN the backend process exits (gracefully via SIGTERM/SIGINT or crash), all FFmpeg preview processes SHALL be terminated. Signal handlers SHALL ensure child process cleanup on graceful shutdown.
12. THE Preview WebSocket endpoints SHALL require authentication via the existing HttpOnly JWT cookie. The browser automatically includes cookies on WebSocket upgrade requests to same-origin paths — no manual token handling is required in the frontend. THE Backend SHALL extract and validate the JWT from the `Cookie` header on the HTTP upgrade request before completing the WebSocket handshake. Invalid or expired tokens SHALL result in immediate connection closure with code 4401. This is consistent with how Socket.io authentication works in the existing system — cookies are sent automatically by the browser on all same-origin connections routed through Caddy.
13. THE Backend SHALL verify the NDI SDK is available at startup by attempting to dynamically import the `grandiose` native module (via `import()` with try/catch — NOT a static import or hard dependency in `package.json`). This ensures `npm install` succeeds on machines without C++ build tools or the NDI SDK. IF the module fails to load, THE Backend SHALL log a clear ERROR message: "NDI SDK not available — camera features are disabled. Install the NDI SDK to enable cameras." THE Backend SHALL emit a persistent Banner-level notification with the same message. All camera features (video preview, PTZ control, presets) SHALL be unavailable — cameras require NDI. The rest of the system (OBS, streaming, lower thirds) SHALL be unaffected. This follows the same graceful degradation pattern as missing FFmpeg.
14. THE Backend SHALL enforce a maximum of `MAX_PREVIEW_STREAMS` (code constant, default: 4) simultaneous FFmpeg preview processes. WHEN the limit is reached and a new preview connection is requested, THE Backend SHALL close the WebSocket with code 4503 and reason "Server busy — too many active previews." THE Frontend SHALL display a centered message on the affected widget: "Preview limit reached — close another preview to view this one." Preview FFmpeg processes SHALL run at lower OS scheduling priority than streaming FFmpeg forwarders (the live stream must never be starved by preview transcoding).

### Requirement 2: OBS Stream Preview Widget

**User Story:** As a volunteer, I want to see and hear what OBS is currently streaming directly on my dashboard, so that I can immediately confirm that changes I make (lower thirds, scene switches) are reflected in the live output.

#### Acceptance Criteria

1. THE Frontend SHALL render an "OBS Preview" widget on the dashboard that displays a live video feed of the OBS output. The widget SHALL be registered with widgetId `"obs-preview"` and seeded at 2×2 in the dashboard grid.
2. THE widget SHALL connect to the preview WebSocket endpoint `/preview/obs` when mounted and disconnect when unmounted. Connection establishment SHALL follow the authentication pattern defined in Req 1.12.
3. THE widget's `WidgetContainer` SHALL display a single connection status indicator labeled "Feed" with the following states: (a) green solid dot (`healthy`) — receiving video frames from the preview WebSocket, (b) grey solid dot (`inactive`) — OBS NDI source not configured or DistroAV output not detected, (c) red blinking dot (`unhealthy`) — OBS NDI source is configured but the preview WebSocket connection has failed or frames have stopped arriving for more than 3 seconds.
4. WHEN the OBS NDI source is not configured, THE widget SHALL display a centered message "OBS Preview Not Configured" on a dark background. WHEN configured but unreachable, THE widget SHALL display "OBS Preview Unavailable — check DistroAV NDI output is enabled in OBS". THE widget SHALL attempt to connect to the preview WebSocket whenever the NDI source is configured, regardless of OBS streaming/recording state.
5. THE Backend SHALL make the OBS preview stream available whenever OBS is running with DistroAV NDI output enabled — regardless of whether OBS is streaming, recording, or idle. THE Backend SHALL receive the OBS NDI output feed (via `grandiose`, same pipeline as camera preview) and transcode it for WebSocket delivery. The NDI source name for OBS (e.g., `"OBS-MACHINE (OBS)"`) SHALL be configured in the OBS device's detail panel on `/admin/devices` — a new "Preview (NDI)" field below the existing WebSocket connection fields, with label "NDI Output Name" and placeholder `"OBS-MACHINE (OBS)"`. This decouples preview availability from streaming state — the volunteer can see OBS output at all times (pre-service setup, recording-only sessions, idle monitoring). IF the OBS NDI source is unreachable (DistroAV not enabled, OBS not running), THE widget SHALL display "OBS Preview Unavailable — check DistroAV NDI output is enabled in OBS" in the inactive state. `docs/setup.md` SHALL document DistroAV plugin installation and NDI output configuration as a prerequisite for OBS preview.
6. THE video element SHALL use `object-fit: contain` to preserve the source aspect ratio without stretching. THE video SHALL be centered both horizontally and vertically within the widget's content area. IF the video is portrait (taller than wide relative to the widget), it SHALL be height-constrained with horizontal centering. IF landscape, it SHALL be width-constrained with vertical centering. Black letterbox/pillarbox areas SHALL use the widget's background color (`color-surface`).
7. THE widget SHALL overlay a mute/unmute button in the bottom-right corner of the video area. The button SHALL be a 3rem × 3rem touch target with a semi-transparent background (`rgba(0, 0, 0, 0.5)`). The button SHALL display a speaker icon (muted) or speaker-wave icon (unmuted) using Ionicons (`volume-mute` / `volume-high`). The button SHALL include a persistent label "Local Audio" in small muted text below the icon to clearly indicate this controls only the dashboard preview audio — it has no effect on the broadcast stream heard by viewers.
8. Audio SHALL be muted by default on initial load. WHEN the page is refreshed, audio SHALL reset to muted. The mute state SHALL NOT be persisted across sessions. WHEN the user taps the mute button, audio SHALL toggle between muted and unmuted.
9. WHEN the user taps anywhere on the video area EXCEPT the mute button, THE Frontend SHALL open a large modal titled "Stream Preview". The modal SHALL display the same live video stream at a larger size (filling the modal content area with the same `object-fit: contain` centering behavior). The modal SHALL include the same mute/unmute button (bottom-right, same styling) and a dismiss button. Audio state SHALL be shared between the widget and modal views — unmuting in the modal keeps audio unmuted when the modal is closed.
10. THE modal SHALL continue receiving the same WebSocket stream (not open a second connection). WHEN the modal is dismissed, playback continues in the widget without interruption or reconnection.
11. WHEN the preview WebSocket connection is lost while the widget is visible, THE widget SHALL display a brief "Reconnecting..." overlay on the video and attempt to reconnect with exponential backoff (1s, 2s, 4s, up to 10s max). WHEN reconnection succeeds, playback resumes automatically. AFTER 3 consecutive failed reconnection attempts, THE widget SHALL stop automatic retries and display a "Tap to Reconnect" button centered on the video area. Tapping the button resets the backoff timer and immediately attempts reconnection. This matches the manual-reconnect interaction pattern established by the OBS disconnect modal.
12. THE widget SHALL NOT consume CPU or network resources when it is not on the active dashboard. WHEN the dashboard containing this widget is navigated away from, the WebSocket connection SHALL be closed.

### Requirement 3: Camera Hardware Abstraction Layer

**User Story:** As a system architect, I want a protocol-agnostic camera control interface that abstracts NDI and VISCA differences, so that widgets and presets operate identically regardless of which protocol the camera uses.

#### Acceptance Criteria

1. THE Backend SHALL define a `CameraControlInterface` that normalizes PTZ operations across NDI and VISCA protocols. The interface SHALL expose the following operations: `panTiltSpeed(panSpeed: number, tiltSpeed: number)` for continuous relative movement (speed range: -1.0 to 1.0, 0.0 = stop), `panTiltAbsolute(pan: number, tilt: number)` for absolute positioning (range: -1.0 to 1.0, 0.0 = center), `zoomAbsolute(zoom: number)` for absolute zoom (range: 0.0 to 1.0, 0.0 = wide, 1.0 = telephoto), `focusAuto()` to enable auto-focus, `focusManual(position: number)` to set manual focus (range: 0.0 to 1.0), `stop()` to halt all movement immediately, and `inquirePosition()` returning `{ pan, tilt, zoom, focus, autoFocus }` (or partial results if the protocol doesn't support inquiry for a given axis).
2. THE Backend SHALL implement the `CameraControlInterface` for NDI using the NDI SDK's PTZ functions (via `grandiose` or equivalent Node.js native bindings): `NDIlib_recv_ptz_pan_tilt_speed` for continuous movement, `NDIlib_recv_ptz_pan_tilt` for absolute positioning, `NDIlib_recv_ptz_zoom` for zoom, `NDIlib_recv_ptz_auto_focus` and `NDIlib_recv_ptz_focus` for focus control.
3. THE Backend SHALL implement the `CameraControlInterface` for VISCA over IP using raw TCP/UDP socket communication: `Pan_TiltDrive` with direction and speed bytes for continuous movement, `AbsolutePosition` command for absolute pan/tilt, `CAM_Zoom Direct` for zoom, `CAM_Focus Auto/Manual/Direct` for focus, and inquiry commands (`CAM_PanTiltPosInq`, `CAM_ZoomPosInq`, `CAM_FocusPosInq`, `CAM_FocusAFModeInq`) for position queries.
4. THE Backend SHALL require NDI for camera video preview and VISCA over IP for all PTZ control. Each camera configuration SHALL specify: `ndiSourceName` in metadata (required — the NDI source name for video feed), and VISCA connection details stored in the existing `host` and `port` columns (required for PTZ when pan, tilt, or zoom features are enabled). The NDI library (`grandi`) does not support PTZ commands; all camera movement (pan/tilt speed, zoom absolute, focus, stop) is sent via VISCA over TCP. VISCA is also used for position inquiry polling (every 5 seconds). The NDI receiver (`grandi` with `COLOR_FORMAT_BEST`) handles HX decode for cameras that send compressed NDI streams. Auto-reconnect is attempted on every PTZ command if the VISCA TCP connection has dropped.
5. THE Backend SHALL connect to the camera's NDI source at startup to verify reachability and start the video preview pipeline. THE Backend SHALL also connect to VISCA and probe via `CAM_PowerInq`. IF VISCA connection fails, THE Backend SHALL log a WARNING. VISCA auto-reconnects on the next command attempt.
6. THE Backend SHALL define a camera feature set as a set of toggleable capabilities: `pan`, `tilt`, `zoom`, `focus`, `ai-tracking`, `ai-tracking-zoom`, `ai-tracking-tilt`. Each camera's enabled features are configured by the admin (Req 7). THE Frontend SHALL hide or disable controls for features that are not enabled on the active camera. AI tracking features (`ai-tracking`, `ai-tracking-zoom`, `ai-tracking-tilt`) SHALL only be available when the camera's model is set to a known supported model (not "Generic") — see Req 7.1. AI tracking toggles SHALL be visible only to ADMIN and AvPowerUser roles; AvVolunteer users SHALL NOT see AI tracking controls (though presets that change AI state still function for all roles).
7. THE Backend SHALL maintain a `CameraService` that manages all configured cameras. The service SHALL: (a) connect to each enabled camera on startup via NDI (and VISCA), (b) poll position data at a regular interval — every 5 seconds via VISCA inquiry, (c) broadcast state updates to subscribed frontend clients via Socket.io, (d) handle reconnection with exponential backoff if a camera becomes unreachable.
8. FOR cameras without VISCA configured (NDI-only), THE Backend SHALL maintain authoritative position state based on commands issued through the system. THE Backend SHALL log a warning at startup: "Camera '{label}' uses NDI-only — position state is based on commanded values and may drift if the camera is controlled externally." The admin UI (Req 7) SHALL display this note when no VISCA connection is configured, recommending VISCA pairing for cameras that may be controlled externally.
9. WHEN using VISCA position inquiry, THE Backend SHALL handle cameras that do not support specific inquiry commands gracefully. IF an inquiry returns an error or timeout, THE Backend SHALL mark that axis as "unknown" in the state and log a DEBUG-level message. The UI SHALL display the last known value (or hide the indicator) for unknown axes.
10. THE Backend SHALL implement adaptive pan/tilt speed: the effective speed sent to the camera SHALL be scaled inversely with the current zoom level. The formula SHALL be `effectiveSpeed = requestedSpeed * (1.0 - zoomLevel * ADAPTIVE_SPEED_DAMPING)` where `ADAPTIVE_SPEED_DAMPING` is a code constant defaulting to `0.7`. At full wide (zoom 0.0), speed is 100% of requested; at full telephoto (zoom 1.0), speed is 30% of requested. A global cap `MAX_EFFECTIVE_SPEED` (code constant, default: `0.6`) SHALL clamp the final effective speed regardless of zoom level, preventing violent camera whips at wide angles when the joystick is fully deflected. The camera HAL implementation for each protocol is responsible for mapping the normalized float speed (0.0–1.0) to camera-native speed units (e.g., VISCA 1–24 speed steps). Cameras that reject a speed command (NAK) SHALL be retried once at 50% speed; if still rejected, the command is dropped and a DEBUG-level log is emitted.
11. THE Backend SHALL implement a dead-man's switch for continuous PTZ movement. WHEN a `cts:camera:ptz:move:start` command is received, THE Backend SHALL begin continuous movement and expect `cts:camera:ptz:move:keepalive` events every 200ms from the client. IF no keepalive arrives within `DEADMAN_TIMEOUT_MS` (code constant, default: 750), THE Backend SHALL issue a stop command to the camera. The 750ms default (vs. the 200ms send interval) provides a 3.5× safety margin to absorb WiFi micro-dropouts and tablet JS thread jank without false-triggering on a healthy connection. This value is a tunable constant — if WiFi environments prove unreliable at 750ms, it can be increased without architectural changes. THE Frontend SHALL send `cts:camera:ptz:move:stop` on touch release. This protects against network drops causing runaway camera movement.
12. THE Backend SHALL expose camera state via Socket.io using the established SocketModule pattern. Events: `stc:camera:state` (full state broadcast), `stc:camera:state:update` (single camera delta), `cts:camera:ptz:move:start`, `cts:camera:ptz:move:keepalive`, `cts:camera:ptz:move:stop`, `cts:camera:set` (partial state update — any undefined field is unchanged), `cts:camera:preset:activate`, `cts:camera:ptz:tap-to-center`. The `cts:camera:set` event accepts a payload of `{ cameraId, zoom?, focus?, autoFocus?, aiTracking?, aiTilt?, aiZoom? }` — only provided fields are applied to the camera. All event name constants SHALL be defined in `packages/shared/src/constants/socketEvents.ts`. THE `stc:camera:state` payload SHALL include per camera: `{ cameraId, connected, position: { pan, tilt, zoom, focus } | null, autoFocus, aiTracking, aiTilt, aiZoom, activePresetId: string | null, features: string[], capabilities: { tapToCenter: boolean }, presets: CameraPreset[] }`. THE `emitInitialState` handler SHALL send the state for all configured cameras. THE `CameraService` SHALL emit `bus:camera:state:changed` on the EventBus whenever camera state changes (position, connection, toggles, active preset). THE `CameraSocketModule` subscribes to this event to broadcast updates — consistent with the EventBus subscription pattern used by all other socket modules. THE Backend SHALL enforce role restrictions on `cts:camera:set` fields: WHEN the authenticated user's role is AvVolunteer, the `aiTracking`, `aiTilt`, `aiZoom`, `autoFocus`, and `focus` fields SHALL be silently ignored (stripped from the payload before processing). Only `zoom` is accepted from AvVolunteer users. This enforces the same restriction the UI applies, preventing bypass via direct socket messages.

13. THE Backend SHALL implement AI tracking control via model-specific HTTP APIs. WHEN a camera's model is set to a known supported model (not "Generic"), THE `CameraService` SHALL use the model-specific driver to send AI tracking commands. FOR the Tongveo NVS20A-4KN model, THE Backend SHALL send HTTP POST requests to the camera's web interface at `http://{host}/api/aiControl` with JSON body: `{ "ai_on": "1"|"0", "ai_enable": "1"|"0", "ai_mode": "1", "ai_auto_zoom": "1"|"0", "ai_auto_tilt": "1"|"0" }`. The `ai_on` and `ai_enable` fields map to the `ai-tracking` toggle (both "1" when enabled, both "0" when disabled). The `ai_auto_zoom` field maps to the `ai-tracking-zoom` toggle. The `ai_auto_tilt` field maps to the `ai-tracking-tilt` toggle. HTTP requests SHALL include the configured cookie in the `Cookie` header. WHEN enabling AI tracking, THE Backend SHALL immediately follow the `aiControl` request with a target selection command: HTTP POST to `http://{host}/api/setPTZCmd` with JSON body `{ "Channel": 0, "PtzCmd": 15, "param1": 7, "param2": 0, "ID": "{configured credential ID}" }`. This tells the camera to track the first detected subject. THE Backend SHALL NOT send the `setPTZCmd` command when disabling AI tracking — only the `aiControl` command is sent when turning AI off. If a configurable delay is needed between the two requests in the future, THE Backend SHALL support a `AI_ENABLE_DELAY_MS` code constant (default: 0) inserted between the `aiControl` and `setPTZCmd` calls. IF the HTTP request fails (timeout, non-2xx response, network error), THE Backend SHALL emit a Toast-level notification: "AI tracking command failed — check camera connection and credentials." and log the error at WARN level.

### Requirement 4: NDI Camera Video Preview

**User Story:** As a volunteer, I want to see a real-time preview of what the camera sees directly on my dashboard, so that I can frame shots accurately without needing a separate monitor.

#### Acceptance Criteria

1. THE Backend SHALL receive the NDI video feed from each configured camera using the NDI SDK (via `grandiose` or equivalent Node.js native bindings) and transcode it to fMP4 for WebSocket delivery using the shared preview infrastructure (Req 1). The NDI source name used for video reception SHALL be the same source configured for PTZ control.
2. THE Frontend SHALL render a "Camera" widget on the dashboard that displays the live camera video feed. The widget SHALL be registered with widgetId `"camera"`. A single widget instance uses a dropdown selector to switch between configured cameras — only one camera feed is active per widget at a time. WHEN multiple cameras are configured, THE widget SHALL include the dropdown selector at the top allowing the volunteer to switch between cameras. WHEN only one camera is configured, the dropdown SHALL be disabled (showing the single camera's name, but not interactive). THE widget SHALL default to the first camera by sort order (alphabetical by label). The selected camera SHALL be persisted in localStorage so the volunteer returns to the same camera on page refresh.
3. THE widget's `WidgetContainer` SHALL display a single connection status indicator labeled "Camera" with states: (a) green solid dot (`healthy`) — connected to the camera and receiving video frames, (b) grey solid dot (`inactive`) — camera is disabled or not configured, (c) red blinking dot (`unhealthy`) — camera is configured but unreachable or video frames have stopped arriving for more than 3 seconds.
4. THE widget SHALL use `ResizeObserver` (per the established pattern) to detect its available size. THE widget SHALL operate in two display modes based on size: (a) **Compact mode** — widget shows video preview only, filling the entire content area; tapping the video opens the full control modal. (b) **Expanded mode** — widget shows video preview filling the available left-side space alongside PTZ controls (defined in Req 5). The video is NOT constrained to a 2×2 grid size in expanded mode — it fills whatever space is available after the controls are allocated.
5. THE threshold for switching between compact and expanded mode SHALL be determined by whether the widget is large enough that a 2×2-cell-equivalent space could fit for the video AND sufficient room would remain for all control elements (virtual joystick, zoom slider, presets list, toggle buttons) at their minimum touch target sizes. The 2×2 reference is only used for threshold calculation — actual video rendering fills available space per Req 4.7. Thresholds SHALL be defined in rem and converted to pixels at runtime using the computed root font size.
6. IN compact mode, THE video element SHALL use `object-fit: contain` with horizontal and vertical centering, identical to the OBS preview widget behavior. The video SHALL expand to fill the widget content area.
7. IN expanded mode, THE video element SHALL occupy a fixed portion of the widget (left side), using `object-fit: contain` with centering. The remaining space SHALL be used for controls (Req 5).
8. WHEN the user taps the video in compact mode, THE Frontend SHALL open a large modal titled "Camera Control" containing the full-size video preview and all PTZ controls (Req 5). The modal SHALL share the same WebSocket stream (no duplicate connection).
9. WHEN the camera is unreachable, THE widget SHALL display a centered message "Camera Offline" on a dark background covering the entire widget content area (both video and controls in expanded mode). WHEN the widget first loads and no frame has been received yet (initial connection in progress), THE widget SHALL display "Connecting..." centered on the dark background (`color-surface`) covering the full widget. This is the state before any camera has ever connected — distinct from the camera-switch freeze-frame behavior in Req 4.10.
10. WHEN the user switches cameras via the dropdown selector, THE Frontend SHALL disconnect from the current camera's preview WebSocket and connect to the newly selected camera's endpoint. The transition SHALL display a "Connecting..." message centered on the video area while the new stream initializes. THE widget SHALL hold the last frame of the previous camera (frozen) beneath the "Connecting..." overlay until the first frame of the new camera arrives, to avoid a jarring black flash.
11. THE widget SHALL NOT consume bandwidth for cameras that are not currently selected in the dropdown. Only the active camera's video stream is subscribed to.
12. THE video preview in this widget does NOT include audio. Camera preview is video-only (unlike the OBS preview which includes audio toggle).

### Requirement 5: Camera PTZ Controls

**User Story:** As a volunteer, I want intuitive pan/tilt/zoom controls for the camera with tap-to-center on the video, so that I can frame shots quickly and accurately during a live service.

#### Acceptance Criteria

1. THE PTZ controls SHALL be visible in the camera widget when in expanded mode (Req 4.4b) and always visible in the full-screen "Camera Control" modal. The controls layout SHALL match the following arrangement: video preview on the left; virtual joystick, zoom slider, and toggle buttons on the right; preset list below or beside the zoom slider (space permitting).
2. THE pan/tilt control SHALL be a virtual joystick — a circular touch zone where the user drags from center to indicate direction and speed. The joystick area SHALL have a minimum diameter of 7.5rem (120px at base) to provide adequate touch area. The distance from center to the edge of the joystick determines speed (0.0 at center to 1.0 at edge). The angle determines direction, naturally supporting diagonal movement. A visible indicator dot SHALL track the user's finger position within the joystick bounds. The joystick SHALL display a subtle dead-zone ring at 15% radius using `color-border` at reduced opacity — this gives the volunteer a visual cue of where movement begins without being distracting. The joystick SHALL be styled as a circular area with a subtle border (`color-border`) and the indicator dot using `color-primary`. The joystick SHALL respond identically to mouse events (mousedown/mousemove/mouseup) for development and non-touch admin use.
3. WHEN the user touches and drags within the joystick area, THE Frontend SHALL emit `cts:camera:ptz:move:start` with the calculated pan/tilt speed values (derived from angle and distance) and begin sending `cts:camera:ptz:move:keepalive` every 200ms with updated speed values as the finger moves. WHEN the user lifts their finger, THE Frontend SHALL emit `cts:camera:ptz:move:stop`. Movement is continuous for the duration of the touch — not discrete steps. THE Frontend SHALL apply a dead-zone of 15% of the joystick radius — finger positions within this zone are treated as (0, 0) and do not initiate movement. THE Frontend SHALL quantize speed values to 0.05 increments (rounding to nearest) and only emit a keepalive if the quantized value differs from the last-sent value. This prevents servo jitter from finger tremor. On socket reconnect during an active move session, THE Backend SHALL treat the reconnection as an implicit stop (speed = 0, 0). The client must initiate a fresh `cts:camera:ptz:move:start` to resume movement — stale keepalives from a previous session are ignored.
4. THE zoom control SHALL be an absolute-position slider oriented vertically (telephoto at top, wide at bottom). The slider SHALL use `ion-range` and have a minimum height of 10rem for the track and a minimum width of 2.75rem for the touch target. The slider's current value SHALL reflect the camera's actual zoom position (synced via polling per Req 3.7b). WHEN the user drags the slider, THE Frontend SHALL emit `cts:camera:set` with `{ cameraId, zoom }` containing the absolute zoom value (0.0 to 1.0).
5. THE Frontend SHALL display the following toggle buttons, each with a minimum height of 2.75rem: (a) **AI Tracking** — toggles the camera's AI auto-tracking mode (ADMIN and AvPowerUser only), (b) **AI Tilt** — when enabled, allows AI tracking to control the tilt axis (ADMIN and AvPowerUser only), (c) **AI Zoom** — when enabled, allows AI tracking to control the zoom axis (ADMIN and AvPowerUser only), (d) **Auto Focus** — toggles between auto-focus and manual focus mode (ADMIN and AvPowerUser only). Toggles SHALL use the established Ionic toggle component pattern. AvVolunteer users SHALL NOT see any of the AI tracking toggles — these are hidden, not greyed out.
6. THE Auto Focus toggle and the manual focus control SHALL be visible only to ADMIN and AvPowerUser roles. AvVolunteer users SHALL NOT see focus controls or AI tracking controls.
7. WHEN Auto Focus is enabled, THE manual focus control SHALL be greyed out (disabled) and non-interactive. WHEN Auto Focus is disabled, a focus slider (`ion-range`, horizontal, minimum height 2.75rem) SHALL allow manual focus adjustment. THE slider SHALL emit `cts:camera:set` with `{ cameraId, focus }` containing the absolute focus value (0.0 to 1.0).
8. WHEN AI Tracking is enabled, THE AI Tilt and AI Zoom toggles SHALL become visible (to ADMIN/AvPowerUser). WHEN AI Tracking is disabled, THE AI Tilt and AI Zoom toggles SHALL be hidden.
9. WHEN the controls are visible (expanded mode or modal) AND the camera has VISCA configured (enabling accurate position tracking), THE user SHALL be able to double-tap on the video preview to command the camera to center on the tapped point. A double-tap is defined as two taps within 400ms on the same target area. THE location of the second tap determines the target point — the first tap registers intent, the second confirms and provides coordinates. This prevents accidental camera movement from single taps on the large video area. THE Frontend SHALL set `touch-action: manipulation` on the video container to suppress browser double-tap-to-zoom behavior. THE Frontend SHALL calculate the second tap's coordinates as a proportional offset from the center of the video element (range: -1.0 to 1.0 on each axis) and emit a `cts:camera:ptz:tap-to-center` event with the offset values. THE Backend SHALL calculate the target absolute pan/tilt position using: `targetPan = currentPan + (tapOffsetX * horizontalFovFraction)`, `targetTilt = currentTilt + (tapOffsetY * verticalFovFraction)`, where `horizontalFovFraction` and `verticalFovFraction` are derived from the camera's configured field-of-view at the current zoom level. THE Backend SHALL then issue an absolute pan/tilt command to the camera. WHEN the camera does NOT have VISCA configured (NDI-only, no accurate position data), double-tapping on the video SHALL display a Toast: "Tap-to-center is not available for this camera. Use the joystick or activate a preset." THE `stc:camera:state` payload SHALL include a `capabilities` object per camera containing `tapToCenter: boolean` (derived from whether VISCA is configured). THE Frontend SHALL use this flag to decide whether to show the Toast or issue the command — this is a system-derived capability, not admin-controlled.
10. THE camera's field-of-view parameters (`fovWideAngle` and `opticalZoomRatio`) SHALL be configured per camera by the admin (Req 7). THE Backend SHALL estimate the effective FOV at the current zoom level using: `effectiveFov = fovWideAngle / (1 + zoomLevel * (opticalZoomRatio - 1))`. At zoom 0.0 (wide), this yields `fovWideAngle`; at zoom 1.0 (telephoto), this yields `fovWideAngle / opticalZoomRatio`. This models the non-linear relationship between zoom position and field of view. The result is still an approximation — the volunteer can tap again or use the joystick for fine adjustment.
11. WHEN AI Tracking is enabled and the user double-taps on the video, THE Frontend SHALL display a Toast notification: "Tap-to-center is disabled when AI Tracking is active." The double-tap SHALL be ignored (no command sent to the camera).
12. WHEN AI Tracking is disabled, double-tap-to-center operates normally on both axes (subject to camera feature set per Req 5.14).
13. ALL toggle states (AI Tracking, AI Tilt, AI Zoom, Auto Focus) SHALL be maintained by the backend `CameraService` and broadcast to all connected clients. Toggling on one tablet SHALL immediately reflect on all other tablets viewing the same camera.
14. THE virtual joystick and zoom slider SHALL respect the camera's enabled feature set (Req 3.6). IF `pan` is not in the feature set, horizontal joystick movement SHALL be ignored. IF `tilt` is not in the feature set, vertical joystick movement SHALL be ignored. IF both `pan` and `tilt` are disabled, the joystick SHALL be hidden. IF `zoom` is not in the feature set, the zoom slider SHALL be hidden. IF `focus` is not in the feature set, focus controls SHALL be hidden regardless of role. IF `ai-tracking` is not in the feature set (camera model is Generic or feature disabled by admin), the AI Tracking toggle and its sub-toggles SHALL be hidden regardless of role.

### Requirement 6: Camera Presets

**User Story:** As a volunteer, I want to activate saved camera presets with a single tap, so that I can quickly frame standard shots (pulpit, choir, wide) without manually positioning the camera.

#### Acceptance Criteria

1. THE Frontend SHALL display a preset list in the camera controls area (expanded mode and modal). The list SHALL show up to 3 presets visible at a time with vertical scrolling if more presets exist. Each preset row SHALL display the preset name and an "Activate" button with a minimum height of 2.75rem.
2. WHEN the user taps "Activate" on a preset, THE Frontend SHALL emit `cts:camera:preset:activate` with the preset ID and display a Toast notification: "Moving to {preset name}". The button for the activated preset SHALL highlight using `color-primary` to indicate it is the active preset. No buttons are disabled — the volunteer can tap another preset or use the joystick at any time (new commands override in-progress movement, matching how a physical camera remote works).
3. THE Backend SHALL activate a preset by determining the recall strategy based on the preset's `storedOnCamera` flag: (a) IF `storedOnCamera: true`, THE Backend SHALL issue the camera's native preset recall command (VISCA preset recall with speed parameter, or `NDIlib_recv_ptz_recall_preset` with speed). (b) IF `storedOnCamera: false`, THE Backend SHALL issue absolute position commands from the stored database values: a combined `panTiltAbsolute(pan, tilt)` command plus `zoomAbsolute(zoom)`, plus `focusManual(position)` if auto-focus is off and a focus value is stored. These commands execute simultaneously on the camera — no sequential motion risk.
4. THE Backend SHALL also apply toggle states from the preset: Auto Focus (on/off), AI Tracking (on/off), AI Tilt (on/off), AI Zoom (on/off). These are applied via the appropriate camera control commands after the position commands. AI toggle states in presets are applied regardless of the activating user's role — a volunteer activating a preset that enables AI tracking will correctly configure AI even though they cannot see the toggle directly.
5. WHEN preset activation is sent, THE Backend SHALL broadcast the updated `activePresetId` to all clients immediately (optimistic — the command was issued). THE Frontend SHALL highlight the active preset's button on all connected clients.
6. IF a preset is active (highlighted) AND the user makes any manual change (joystick movement, zoom slider, toggle, or double-tap-to-center), THE active preset indicator SHALL clear. The volunteer relies on the live preview to verify camera position — no "Activated" confirmation state is needed.
7. THE system SHALL NOT attempt to detect whether the camera's current position matches a preset after server restart. On fresh startup, no preset is marked as active — all buttons show "Activate".
8. IF the camera is unreachable when a preset is activated, THE Backend SHALL emit a Toast-level notification: "Camera '{label}' is not responding — check connection." The active preset indicator SHALL still be set (the command was issued; the volunteer sees via preview whether it worked). The volunteer can retry or use manual controls immediately — no lockout period.
9. THE Backend SHALL store presets in a `camera_presets` database table with fields: `id`, `cameraId` (foreign key to the camera device), `name`, `sortOrder` (integer for display ordering), `storedOnCamera` (boolean), `cameraPresetSlot` (integer, nullable — the onboard slot number if stored on camera), `pan` (float, nullable), `tilt` (float, nullable), `zoom` (float, nullable), `focus` (float, nullable), `autoFocus` (boolean), `aiTracking` (boolean), `aiTilt` (boolean), `aiZoom` (boolean), and `createdAt`.
10. NULLABLE position fields (pan, tilt, zoom, focus) indicate that the value could not be captured during preset creation (e.g., camera doesn't support inquiry for that axis). WHEN activating a preset, THE Backend SHALL skip any axis with a null value — the camera retains its current position on that axis.
11. PRESETS are admin-managed (created/edited/deleted via the admin camera configuration page, Req 7). Volunteers can only activate presets — they cannot create, edit, or delete them.
12. THE preset list SHALL be ordered by `sortOrder` ascending. If two presets have the same `sortOrder`, they SHALL be sub-sorted by `name` alphabetically.

### Requirement 7: Camera Admin Configuration

**User Story:** As an administrator, I want to add and configure cameras through the admin UI — including connection settings, feature toggles, and presets — so that volunteers have a ready-to-use camera control experience.

#### Acceptance Criteria

1. THE admin Device Management page (`/admin/devices`) SHALL support a new device type `"camera-ptz"`. WHEN adding a camera, the admin SHALL provide: label, Camera Model (dropdown: "Generic" or a known supported model, e.g., "Tongveo NVS20A-4KN"), NDI source name (required — for video feed and PTZ control; the NDI SDK discovers cameras by name on the LAN via mDNS-like broadcast), optionally VISCA IP address and port (for enhanced position polling accuracy, default port 5500), and wide-angle field of view in degrees (`fovWideAngle`, used for tap-to-center calculations, defaulting to 60°), and optical zoom ratio (`opticalZoomRatio`, the camera's maximum optical zoom multiplier, defaulting to 20). WHEN a non-Generic camera model is selected, THE admin form SHALL display an additional "AI Tracking Configuration" section containing: (a) an HTTP Cookie field (stored encrypted in device config — the admin obtains this from browser dev tools while interacting with the camera's web interface), (b) an API Credential ID field (stored encrypted — the admin obtains this from the request payload in browser dev tools). `docs/setup.md` SHALL document how to obtain the cookie and credential ID from the camera's web interface using browser developer tools, and SHALL warn that these values may expire on camera reboot. WHEN Camera Model is "Generic", AI tracking features (`ai-tracking`, `ai-tracking-zoom`, `ai-tracking-tilt`) SHALL NOT appear in the features section and SHALL be unavailable in the widget. Camera device CRUD uses the existing `/api/admin/devices` endpoints with conditional validation: when `deviceType === "camera-ptz"`, the backend validates that `metadata.ndiSourceName` is present (required) and accepts optional `metadata.cameraModel`, `metadata.fovWideAngle`, `metadata.cameraFeatures`, `metadata.viscaEnabled`, `metadata.aiHttpCookie` (encrypted), and `metadata.aiCredentialId` (encrypted) fields. WHEN VISCA is enabled, the `host` and `port` columns store the camera's IP and VISCA port respectively. WHEN VISCA is not enabled, `host` and `port` are stored as `"127.0.0.1"` and `5500` (placeholders — the user never sees them unless they enable VISCA). The admin form SHALL show VISCA fields as an optional "Position Polling (Recommended)" section with a toggle to enable/disable. IF the NDI SDK is not available (Req 1.13), THE admin page SHALL display a warning: "NDI SDK not installed — camera features are unavailable. Install the NDI SDK to enable cameras." `docs/setup.md` SHALL document NDI SDK installation as a prerequisite for camera features. THE Backend SHALL receive NDI video frames via the `grandiose` native module's receiver API and pipe them to FFmpeg (via stdin) for transcoding to fMP4 — this avoids requiring the separate FFmpeg NDI plugin to be compiled.
2. THE admin device detail panel for cameras SHALL display a "Features" section with toggles for each capability: `pan`, `tilt`, `zoom`, `focus`. WHEN the camera model is not "Generic", additional toggles SHALL appear: `ai-tracking`, `ai-tracking-tilt`, `ai-tracking-zoom`. All toggles SHALL default to enabled for a new camera. Disabling a feature hides or disables the corresponding control in the volunteer-facing widget.
3. WHEN no VISCA connection is configured for a camera (NDI-only mode), THE detail panel SHALL display an informational note: "No VISCA configured — position tracking uses last-commanded values, which may drift if the camera is controlled externally. Adding VISCA provides accurate position feedback for zoom slider and tap-to-center."
4. WHEN the admin saves a camera configuration, THE Backend SHALL attempt to probe the camera on the selected protocol (per Req 3.5). THE admin page SHALL display the probe result: success (green checkmark with "Connected") or failure (red X with the error reason). Probe failure SHALL NOT prevent saving — the admin may be configuring a camera that is currently offline.
5. THE admin device detail panel for cameras SHALL include a "Presets" section listing all configured presets for that camera in their display order. Each preset row SHALL display: name and whether it's stored on camera (badge: "On Camera" or "Software Only"). The list SHALL support drag-to-reorder — the admin drags preset rows into the desired order, and the backend assigns `sortOrder` values (0, 1, 2...) based on the resulting position. Action buttons: Edit, Delete. An "Add Preset" button SHALL be available below the list.
6. WHEN the admin taps "Add Preset" or "Edit" on a preset, THE Frontend SHALL open a modal titled "Configure Preset" (for new) or "Edit Preset: {name}" (for existing). The modal SHALL contain: (a) a Name text input, (b) a "Store on Camera" toggle with a camera slot number input (visible when toggled on), (c) the same PTZ controls as the volunteer widget (virtual joystick, zoom slider, toggle buttons including focus) so the admin can position the camera interactively, (d) a live video preview of the camera showing the current framing, (e) a "Capture Position" button.
7. WHEN the admin taps "Capture Position", THE Backend SHALL poll the camera's current position values and store them in the preset. The following values SHALL be captured: Pan position (from VISCA inquiry or last-commanded NDI value), Tilt position (same), Zoom position (same), Focus position (only if Auto Focus is off; gracefully returns null if inquiry fails), Auto Focus state (from the toggle in the modal), AI Tracking state (from the toggle), AI Tilt state (from the toggle), AI Zoom state (from the toggle). THE Frontend SHALL display a brief "Captured" confirmation on the button.
8. IF a position value cannot be captured (inquiry fails or NDI-only without commanded history), THE value SHALL be stored as null. THE admin SHALL be informed which values were captured vs. null via a summary display (e.g., "Pan: -0.32, Tilt: 0.15, Zoom: 0.45, Focus: N/A").
9. WHEN "Store on Camera" is toggled on and a slot number is provided, THE Backend SHALL write the preset to the camera's onboard storage using the appropriate command (VISCA `preset_set` or `NDIlib_recv_ptz_store_preset`). IF the write fails, THE Backend SHALL display an error in the modal and revert the "Store on Camera" toggle.
10. THE admin SHALL be able to delete presets with a confirmation dialog: "Delete preset '{name}'? This cannot be undone." IF the preset is stored on camera, the deletion SHALL only remove it from the database — the camera's onboard memory is not cleared (to avoid accidentally erasing a preset that may be used by other control systems).
11. THE Backend SHALL expose REST endpoints for camera preset CRUD operations: `GET /api/admin/cameras/{cameraId}/presets`, `POST /api/admin/cameras/{cameraId}/presets`, `PUT /api/admin/cameras/{cameraId}/presets/{presetId}`, `DELETE /api/admin/cameras/{cameraId}/presets/{presetId}`, `PUT /api/admin/cameras/{cameraId}/presets/order` (accepts an ordered array of preset IDs; index becomes `sortOrder`). All endpoints SHALL require the ADMIN role. A capture endpoint `POST /api/admin/cameras/{cameraId}/capture-position` SHALL return the camera's current position values for preset creation. This follows the `/api/admin/` namespace convention used by all other admin-only endpoints.
12. WHEN a camera's presets are modified (created, edited, deleted), THE Backend SHALL broadcast the updated preset list to all connected clients via Socket.io so volunteer widgets reflect changes immediately without page refresh.

## Accepted Risks

The following risks have been evaluated and explicitly accepted for this release:

### Risk 1: NDI-Only Position Drift (No VISCA Configured)

For cameras without VISCA configured, the system tracks position based on commands issued through the system. If the camera is moved externally (physical joystick, another control system), the backend's position model drifts from reality. Tap-to-center and preset capture may produce incorrect results. This is accepted because: (a) the admin UI clearly recommends VISCA pairing when this is a concern, (b) activating a preset re-anchors to absolute values, (c) the volunteer can always use the joystick for fine correction after tap-to-center, and (d) adding VISCA at any time immediately upgrades to accurate polling with no other changes needed.

### Risk 2: Camera Widget at 6×4 Dominates the Dashboard

The camera widget occupies 60% of horizontal and 67% of vertical grid space at the seeded 6×4 size. This leaves limited room for other widgets (OBS controls, lower thirds, OBS preview). This is accepted because: (a) the camera operator is typically a dedicated role — they need the camera widget as their primary interface, (b) widgets can be rearranged via admin configuration for different dashboard layouts (e.g., a "camera operator" dashboard vs. a "stream manager" dashboard), and (c) compact mode is available for smaller widget placements.

### Risk 3: Multi-Client PTZ Command Conflicts

When two clients send conflicting PTZ commands to the same camera simultaneously, the behavior is last-writer-wins with non-deterministic arrival order. This matches the precedent set in `livestream-control-system` Requirement 22 (Concurrent Command Non-Determinism). Both clients receive the reconciled state via normal Socket.io broadcast. This is accepted because: (a) the typical deployment has one camera operator per camera, and (b) conflicting commands are self-correcting (the volunteer sees the result and adjusts).

### Risk 4: Preview WebSocket Cookie Expiry on Long Sessions

Preview WebSocket connections authenticate via the HttpOnly JWT cookie. If the JWT expires mid-session (default 8h), the connection will be closed with code 4401 on the next reconnection attempt. The volunteer must refresh the page to re-authenticate. This is accepted because: (a) services rarely exceed 3 hours, (b) the 30-day "Remember me" option covers multi-service days, and (c) the reconnection logic will surface the issue clearly (exponential backoff with "Reconnecting..." overlay, eventually showing unhealthy indicator).

### Risk 5: FFmpeg Cold-Start Latency

The on-demand FFmpeg spawning means the first client to view a preview source experiences 2-5 seconds of delay before video appears (process spawn + source negotiation + first keyframe). This is accepted because: (a) the 3-second grace period prevents thrashing on page refresh, (b) the "Connecting..." transitional state sets expectations, and (c) once running, subsequent clients get instant video via fan-out. A future optimization could pre-warm FFmpeg for cameras that have presets configured.

### Risk 6: DistroAV Plugin Required for OBS Preview

OBS preview requires the DistroAV (NDI) plugin installed in OBS with NDI Main Output enabled. If an admin forgets this setup step, the OBS Preview widget shows "OBS Preview Unavailable" with a clear message pointing to the fix. This is accepted because: (a) DistroAV is free, cross-platform, and trivial to install via package managers, (b) it's a one-time setup documented in `setup.md`, (c) the benefit (preview always available regardless of stream/record state) outweighs the setup cost, and (d) the same NDI Runtime is already required for camera features.
